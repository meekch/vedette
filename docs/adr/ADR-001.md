# ADR-001 — Supabase client as the data access layer (no Prisma / no ORM)

- **Status:** Accepted
- **Date:** 2026-07-22
- **Deciders:** Technical lead (Phase 0)
- **Context source:** `CLAUDE.md` (pinned stack), `docs/CHARTER.md`, `docs/schema.sql`

## Context

Vedette is multi-tenant from day one, and the tenant boundary is enforced by **Postgres Row Level Security**, not by application code (see `docs/schema.sql` §7). The data layer's most important job is therefore *not* ergonomic query building — it is preserving RLS as the single source of truth for who can see what. Every read/write on behalf of a user must travel with the user's Clerk JWT so Postgres can evaluate `auth.org_id()` per statement.

We also lean heavily on Postgres-native features that live outside the typical ORM's comfort zone: `pgvector` similarity search, `jsonb` deliverable/document payloads, enum types, `SECURITY DEFINER` helper functions, and RLS policies themselves.

## Decision

Use the **Supabase JS client** as the data access layer. **No Prisma, no Drizzle, no ORM.** Concretely:

- Three clients, by trust level (see `lib/supabase/`): a **server user-scoped** client that forwards the Clerk JWT (RLS-enforced, the default for all user-driven reads/writes); a **browser** client (anon key, RLS-enforced, no secrets); and a **service-role** client that bypasses RLS, confined to Clerk webhooks and ingestion jobs.
- Hand-written, typed query modules in `src/db/`, using **Supabase-generated TypeScript types** for row/insert/update shapes.
- `pgvector` retrieval via a Postgres RPC (`match_chunks`) called through the client.
- Schema changes as plain SQL migrations under `supabase/migrations/`, derived from `docs/schema.sql`.

## Consequences

**Positive**
- RLS stays authoritative. The client passes the JWT straight through; there is no ORM connection pool running as a privileged role that would quietly sidestep policies.
- First-class access to pgvector, jsonb, enums, RPCs, and Storage without fighting an ORM abstraction or waiting on ORM support for Postgres features.
- One mental model. The SQL in `schema.sql` *is* the schema; there is no second schema definition in an ORM DSL to drift out of sync.
- Smaller dependency surface and no ORM query-engine binary in the build.

**Negative / costs**
- We write SQL and typed query modules by hand instead of getting a fluent query builder and automatic migrations. More boilerplate for complex joins.
- Type safety depends on regenerating Supabase types after every migration (a CI step); forget it and types drift from the DB.
- No ORM-level relation loading — we compose queries/RPCs deliberately. This is a feature for RLS clarity but a cost for developer speed on deep object graphs.

**Mitigations**
- `src/db/` centralizes queries so raw SQL isn't scattered through components.
- CI regenerates and typechecks Supabase types on every schema change.
- Heavy read paths (retrieval, evidence expansion) become named Postgres RPCs, keeping app code thin and the query planner-visible.

## Alternatives considered

- **Prisma** — best-in-class DX and migrations, but its RLS story is awkward (it historically runs through a pooled privileged connection and does not forward per-request JWT claims cleanly), it lags on `pgvector`, and it would introduce a *second* schema definition competing with our SQL. Rejected: it fights the one guarantee we care most about.
- **Drizzle** — lighter and SQL-forward, closer in spirit, and a reasonable future revisit. Rejected for Phase 0 only to avoid adding an abstraction over the Supabase client that the pinned stack already standardizes on; not a hard "no" forever, but changing it would need a superseding ADR.
- **Raw `pg` / Kysely** — maximum control, but throws away Supabase's generated types, auth integration, Storage, and RPC ergonomics that we get for free.

## Compliance / how we'll know it held

- No ORM dependency appears in `package.json`.
- No user-facing read/write path uses the service-role client (grep + review).
- RLS policy tests (in `tests/`) prove cross-tenant reads return zero rows.
