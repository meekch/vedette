# ADR-002 — Clerk for authentication and organizations

- **Status:** Accepted
- **Date:** 2026-07-22
- **Deciders:** Technical lead (Phase 0)
- **Context source:** `CLAUDE.md` (pinned stack), `docs/architecture.md` §4

## Context

Vedette needs, on day one: email/SSO sign-in, **organizations with roles** (a consultancy or enterprise account with owner/admin/member/viewer), an org switcher, and — critically — a **session JWT that RLS can read** to resolve the current tenant. Auth is on the critical path for the multi-tenant guarantee (ADR-001, `schema.sql` §7): if identity and the `org_id` claim are wrong, RLS is meaningless.

We explicitly do *not* want to build auth: password resets, session management, SSO/SAML, MFA, and org membership UIs are undifferentiated heavy lifting with real security risk.

## Decision

Use **Clerk** for authentication and organization management, integrated with Supabase as a **third-party auth provider**:

- Clerk is the **source of truth for identity and org membership**. Its prebuilt components handle sign-in, org creation, invitations, and the org switcher.
- Clerk's **session token is configured to include an `org_id` claim** (`{{org.id}}`) and the user id in `sub`. Supabase is configured to trust Clerk and validates the token via **JWKS**. RLS reads these claims through `auth.jwt()` (see `auth.org_id()` / `auth.org_role()` in `schema.sql`).
- A **Clerk webhook** (`/api/webhooks/clerk`) mirrors orgs, users, and role changes into our local `organizations` / `users` tables (via the service-role client) so we can foreign-key to local rows and attach org-scoped profile data. Clerk remains authoritative for *authentication*; the mirror is a convenience for *relational integrity*.
- The Next.js middleware protects the `(app)` route group; unauthenticated users are redirected.

## Consequences

**Positive**
- We inherit production-grade auth (SSO/SAML, MFA, session security) and a full **organizations + roles** model without building it — this directly serves the FDE-firm-as-tenant model.
- Clean RLS integration: the same JWT that authenticates the request also carries the tenant claim, so there is exactly one identity path.
- Fast Phase 1: Clerk's components mean the auth surface is mostly configuration.

**Negative / costs**
- **Two systems of record** for users/orgs (Clerk + our mirror). The webhook must be reliable and idempotent, and we need a reconciliation/backfill path for missed events.
- Vendor lock-in on identity; migrating off Clerk later means re-homing users and re-issuing the claim contract that RLS depends on.
- The `org_id` claim wiring is a small but **load-bearing** configuration detail — if the claim key or Clerk third-party-auth setup is wrong, every RLS policy silently returns nothing. (Flagged as an open question for Phase 1 kickoff.)
- Cost scales with monthly active orgs/users; fine at portfolio/engagement scale, worth watching at enterprise scale.

**Mitigations**
- Webhook handlers are idempotent (upsert by `clerk_org_id` / `clerk_user_id`) and we add a manual reconcile command for drift.
- The claim contract lives in one place (`auth.clerk_org()` / `auth.clerk_user()` helpers), so if the claim shape changes we fix it once.
- An RLS integration test asserts that a valid Clerk JWT resolves to exactly one org and that a missing/foreign claim yields zero rows.

## Alternatives considered

- **Supabase Auth (GoTrue)** — native, zero JWT-bridging, and the "obvious" pairing with Supabase. Rejected because its **organizations/roles** story is roll-your-own (memberships, invites, org switcher all hand-built), which is exactly the surface Clerk gives us for free and which our FDE tenancy model leans on heavily. Revisitable if the Clerk mirror proves more trouble than it's worth.
- **Auth0** — comparable capability, heavier and pricier for this stage, weaker Next.js App Router ergonomics than Clerk today.
- **NextAuth/Auth.js** — flexible and free, but org/role management and enterprise SSO become our problem, reintroducing the work we're trying to avoid.

## Compliance / how we'll know it held

- `auth.org_id()` returns the caller's org for a valid Clerk JWT in an integration test; a foreign/absent claim returns null → zero rows.
- Webhook is idempotent (replaying an event is a no-op) and covered by a test.
- No auth logic beyond configuration + the webhook + middleware lives in the app.
