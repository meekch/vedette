# ADR-005 — Embedding model: OpenAI text-embedding-3-small (1536 dims, cosine)

- **Status:** Accepted
- **Date:** 2026-07-22
- **Deciders:** Technical lead (Phase 0)
- **Context source:** `docs/architecture.md` §9 (open questions), `docs/schema.sql` (`chunks.embedding`), ADR-003 (Vercel AI SDK)
- **Resolves:** Open question #1 from the Phase 0 handoff (embedding model + vector dimension).

## Context

The Knowledge Engine (Phase 2) chunks uploaded documents and stores an embedding per chunk in `chunks.embedding` for semantic retrieval — the backbone of the evidence system, since every retrieved chunk is a potential citation. Phase 0 left the embedding model open, which blocked two concrete schema commitments: the **vector dimension** (fixed by the model) and the **HNSW opclass** (distance metric). We need both pinned before the first migration so the index and column don't churn.

Requirements: good retrieval quality on messy enterprise documents (SOPs, transcripts, ticket exports), low cost at ingestion scale, and a call path that fits our stack — the Vercel AI SDK (ADR-003), which has a first-class OpenAI embeddings provider.

## Decision

Use **OpenAI `text-embedding-3-small`**, **1536 dimensions**, with **cosine distance** for the HNSW index (`vector_cosine_ops`).

- Called through the **Vercel AI SDK** embeddings interface (`embed` / `embedMany`), consistent with ADR-003 — no separate embedding SDK.
- `chunks.embedding` is typed `vector(1536)`; the HNSW index uses `vector_cosine_ops` (see `docs/schema.sql`).
- **Upgrade path is documented, not built:** if Phase 2 dogfooding shows weak retrieval on real client documents, **Voyage AI** (e.g. `voyage-3`) is the pre-vetted upgrade. Voyage consistently tops retrieval benchmarks for this kind of corpus. Switching means a new dimension, a re-embed of the corpus, and an opclass review — a migration, hence an ADR trigger, not a config flip.

## Consequences

**Positive**
- **Industry-default cost/quality.** `text-embedding-3-small` is cheap enough to embed whole document sets without budget anxiety and strong enough for first-pass retrieval, letting us prove the end-to-end evidence loop before optimizing.
- **Zero new dependencies.** Reuses the OpenAI provider already in the AI SDK; one provider config, one place to swap models.
- **Schema unblocked.** Dimension (1536) and opclass (cosine) are now concrete, so the first migration is stable.
- Cosine is the recommended metric for OpenAI embeddings (they are normalized), so `vector_cosine_ops` is the correct default rather than a guess.

**Negative / costs**
- `text-embedding-3-small` is not state-of-the-art on retrieval; on genuinely messy or domain-specific corpora it may under-retrieve versus Voyage or `text-embedding-3-large`. We accept first-pass quality now and hold Voyage in reserve.
- The dimension is baked into the column and index. Changing models later (to Voyage or `-3-large` at 3072 dims) requires re-embedding every chunk and rebuilding the index — a real migration, not a toggle.
- Ties ingestion to OpenAI availability/pricing for the embedding path even if chat models come from another provider.

**Mitigations**
- The embedding call is isolated behind one function in the ingestion pipeline, so the model id and dimension live in one place.
- The Phase 2 dogfood checkpoint (`PHASES.md`) explicitly tests retrieval on anonymized real documents — that is the decision point for triggering the Voyage upgrade ADR.

## Alternatives considered

- **OpenAI `text-embedding-3-large` (3072 dims)** — higher quality, ~2× cost and storage, larger index. Rejected for now: the small model is enough to validate the loop; if we need more quality we'd likely jump to Voyage rather than pay for large.
- **Voyage AI (`voyage-3` family)** — best-in-class retrieval for enterprise/document corpora, but adds a provider and cost before we've proven we need it. Chosen as the **documented upgrade path**, not the default.
- **Open-source / self-hosted (e.g. `bge`, `nomic-embed`) via a local runtime** — cheapest at scale and no per-call fee, but adds hosting/ops burden that fights the "prove the loop first" goal and the serverless Vercel deployment. Rejected for Phase 2; reconsiderable at scale.
- **Cohere `embed` v3** — strong and viable, but no advantage over the OpenAI-default-now / Voyage-upgrade-later path, and it adds a provider. Rejected.

## Compliance / how we'll know it held

- `chunks.embedding` is `vector(1536)` and the HNSW index uses `vector_cosine_ops` (`docs/schema.sql`).
- Embeddings are produced via the Vercel AI SDK (no separate embedding SDK in `package.json`).
- The model id lives in exactly one place in the ingestion pipeline.
- A switch away from `text-embedding-3-small` is recorded as a superseding ADR (it implies a re-embed migration).
